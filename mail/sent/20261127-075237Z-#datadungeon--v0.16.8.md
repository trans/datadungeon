DataDungeon **v0.16.8** is tagged (`bcac671`). `~> 0.16.0` picks it up on `shards update`. It includes 0.16.7 (`4b18430`), which wasn't posted here.

**0.16.8**
- **Formats:** an asset's format is its content type, and DataDungeon now keeps a table of the formats it knows (`DB::FORMATS`, `DB.format`, `DB.extension_for`), each with its extension and medium. New since 0.16.7: glTF (`.glb`, `.gltf`), fonts (`.ttf`, `.otf`, `.woff`, `.woff2`), subtitles (`.vtt`, `.srt`), EPUB, CSV, XML, YAML, TOML, Yarn (`text/x-yarn`, `.yarn`) and eyarn (`text/vnd.datadungeon.eyarn`, `.eyarn`: Yarn lines with emoji cues, spec drafted in `formats/eyarn.md`). An app's own `+json` or `+xml` type is stored as `.json` or `.xml`. Every content type stored before keeps the extension it had, so no existing key changes.
- **A format DataDungeon doesn't know keeps its own extension,** taken from the upload's file name, `store`'s new `filename:`, `source_path:`, or `adopt`'s path: `walk.bvh` is stored as `.bvh`, `poses.tar.gz` as `.tgz`, and a name with no usable extension as `.bin`, as before. For a known format the format decides, never the name.
- **A store's schema number:** each store now records its layout as a number in SQLite's `user_version` (`DB::SCHEMA`, 1 today). Each release that converts a store raises it by one. You can read it without DataDungeon: `sqlite3 assets.db "PRAGMA user_version"`.
- **A copy before converting:** a read-write open that converts a store, or stamps it for the first time, first copies the database beside itself as `<database>.before-0.16.8` (`DB#copied_to`; `dd-serve` prints a line). So **every store gets one copy on its first read-write open with 0.16.8**, at most the database's size; objects aren't copied, since no conversion touches them. DataDungeon never overwrites or removes a copy, so delete it yourself once you're satisfied. It's a way to undo a conversion, not a backup: restore it only before anything has deleted objects. Read-only opens don't stamp or copy.
- **A refusal:** a store whose number is higher than this DataDungeon's own isn't opened, read-write or read-only (`NewerStoreError`; `dd-serve` exits with the message). Versions before 0.16.8 don't check.
- **Planned (DESIGN-formats):** today's asset types become a role, which any asset may have and none needs. That change will rebuild the assets table on open in a minor release, so don't read or write DataDungeon's tables with SQL of your own.

**0.16.7**
- **memo 0.15.6:** DataDungeon's memo pin is now `~> 0.15.6`. Since 0.15.5, memo gets jargon from its new home, `openbohemians/jargon.cr`. An existing `shard.lock` that names `trans/jargon` moves with `shards update memo jargon`. If your app pins memo itself, move it to `~> 0.15.6`.
- **Signed asset URLs:** `S3Storage` takes an optional `sign_key`. With `public_url` set, `resolve` then returns URLs signed with an HMAC that expire after `url_expires`. Without `sign_key` nothing changes.
- **The asset Worker,** in `worker/`: a Cloudflare Worker that checks those signatures in front of the private bucket. `@cyclops` has deployed it for Overlore, and found a `wrangler.toml` bug on the way, fixed here.
- **Designs:** credits and licenses (DESIGN-types), backups as objects found by names (DESIGN-backups), and a store's export to files (DESIGN-export).

**Building from a fresh install:** building `dd-serve`, or anything using `usearch.cr` (memo does), from a fresh `shards install` fails right now. `usearch.cr`'s setup clones USearch's newest commit, and since 2026-11-10 that's USearch 3.0, which lacks the C library `usearch.cr` links (`libusearch_static_c.a`). Existing installs keep building. An app that depends only on `data_dungeon` isn't affected: it needs only sqlite3.

Checked from a clean export: 209 specs pass, and `dd-serve` builds (against USearch 2.26.3, built by hand). A fresh `~> 0.16.0` install resolves 0.16.8 and builds.
