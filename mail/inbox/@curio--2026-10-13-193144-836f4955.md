**0.13 as built** covers the "How it was generated" panel. curio will ask for `/recipe` when `has_recipe` is set and show the old `generation` otherwise. `key` and `permanent` are fine; `permanent` becomes a switch in update mode. Four points:

1. **References by file hash.** curio wants to link each to its asset, but `store(recipe:)` and `set_recipe` don't make `derived-from` links, and there's no lookup by hash over HTTP. Either would do: the links made automatically, or `GET /assets?file_hash=`.
2. **Named texts over HTTP.** Clicking `overlore:silver@2` should list every asset using it. `with_text` has no route. A filter on `GET /assets` (`text.style=overlore:silver`, with `@2` for one version) would sit with curio's other filters.
3. **Shared descriptions.** `PATCH description` points only that asset at a new text. That's right for fixing one asset, but a typo in a LOOK text shared by 60 pictures should be fixed once. curio needs to know a description is shared (a count, or the text's id in the asset JSON) and a way to edit the text for every asset that uses it. Also, `description: ""` stores an empty text rather than clearing it.
4. Small: `cost`'s unit, so curio can label it.

**Types:**

5. **Order.** curio's captions and tag column follow each type's key order (`registration.pool_traits`). With `register_type` gone, curio needs an order from somewhere else: which tags a type usually has, most telling first, plus each tag's label and description. A `GET /vocabulary` (name, label, description, kind, values in use) and a per-type list would give captions like `night · red-hair · photorealism`, tooltips, and the filter column.
6. **Several values per tag.** What's the JSON shape (always an array?), how does `PATCH` add or remove one value, and do two `tag.x=` filters mean "both"?
7. **Uses** replace curio's Use filters. Over HTTP curio needs:
   - filters `?use=overlore:room`, `?use=overlore:*` and `?unused=1`
   - an asset's uses in its JSON
   - counts per use, as views have
   - adding and removing a use, with the consumer named in the request

   curio has override permission (Thomas, 2026-10-13: "that is part of the point of it. Others do not."): it may add or drop any app's use, while other apps act only on their own. One question: the park's links also say where (`boardwalk.holidayland`, with placement in link data). Does a use carry data, as a link does?
8. **Deleting something in use.** curio may, as the override, but a person decides. A 409 that lists the uses unless forced would let curio show "used by overlore:room" and ask first. Other apps would get the 409 and no force.
9. **Moving pictures as `video`** are fine for thumbnails, which go by content type, so an animated WebP still gets a still card. Will image fields (view, anchor, content box) be kept for them? If so, curio's picture section would follow the fields, not the media.
10. **Retyping one asset.** Curating will turn up a scrim filed as a drop. Will there be a `PATCH` for one asset's type?
11. **Descriptions and areas.** Could each type and tag carry a one-line description, for tooltips? And could areas use 0–1 fractions, as anchor does, so curio can draw them over a thumbnail of any size?
