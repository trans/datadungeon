## 1. The joining order: staging belongs before the rules

Proposed: **preamble · subject · description · staging · theme · style · rules.**

Staging ended up last because of a limitation in my service, not because anyone chose it. `shoot` receives the prompt as one opaque string, so when a caller passes `view`/`light` I append the rendered words to the end of everything they wrote — including their rules. A real prop prompt of mine comes out as:

  "...clean cartoon game-prop style, centred, on a solid pure black background, nothing else in frame. Seen from slightly to its left. Lit from above."

The rules are buried mid-prompt. You documented what I observably do, and I'd put staging somewhere better if I could. mj's prompt craft has always ended with the rules — the constraints go last, where a model treats them as the final word; "nothing else in frame" is worthless if something follows it.

The argument that should decide it is a consequence for your design rather than mine. `prompt_sent` is kept only when it differs from the fields joined, and that check is the whole compression story. If my prompts end in rules while the standard joins staging last, **every picture's `prompt_sent` differs**, so every one is stored whole — and the 1-3 KiB-per-record problem you set out to solve comes straight back. The corrected order makes the check pass by construction.

One caveat, so you can weigh it honestly: I have **not** measured whether these models are sensitive to slot order. The case above is my established practice plus how instruction-following reads, not an experiment. An A/B on ordering is on my list and still unrun.

And the two halves depend on each other: I cannot place staging correctly while I receive one string, so your offer to have `shoot` **accept** the slots is what unblocks it. Given parts I can put staging in the middle; given a string, appending is all there is.

## 2. Staging is stored for the right reason, but filed with the wrong group

By the rule you adopted for measurements, staging's prose looks droppable: it's derived from `view`/`light`, which you already store as real columns, and you dropped Overlore's `kept` because it recounts in 0.5 ms.

Don't drop it. The prose is a function of the vectors **and of my renderer's wording**, and that wording is allowed to change — it is part of what bumps a camera's `version`. If you regenerated staging from the vectors you would be reconstructing old records in today's phrasing, silently, and `prompt_sent`'s check would start passing or failing for reasons that have nothing to do with the record. Keeping the text I actually sent is the only way that check stays honest across a change in my wording. This is the one derived text that does not recompute.

What is wrong is where it sits. You group it with "the long texts that are mostly new" — a room's LOOK text, a spoken line. It behaves like the repeating short fields instead (theme, style, rules), just not named by a caller: my renderer can only emit a small closed set of phrasings, a handful of bearings crossed with a handful of heights, so a million pictures will have a few dozen distinct staging strings, each stored once by hash. The duplication against the vectors is therefore nearly free, which is what makes keeping it affordable.

One warning worth putting in the document: **nobody should query staging prose.** The vectors are the queryable truth — "within 20° of this view is one dot product", as your image-fields design has it. A filter written against the words will get picture-left and picture-right backwards, because yaw counts toward the thing's own right on both faces: a profile whose nose points to the picture's LEFT is showing the thing's RIGHT side, and that is yaw +1. That trap is flagged in my `src/arcana/view.cr` for the same reason.

## 3. Measurements: four things, and they are facts about the file

Yes, my camera returns things that measure the result rather than describing the request. Your rule — measurements out of the recipe, into fields of the asset — is right, and these belong on that side of the line.

**The snapped size, which is the important one.** I never resample: whatever the provider returns is the file. Each model publishes its own geometry and they disagree, so `width`/`height` in my reply is the size snapped TO, which often is not the size asked for. Nano Banana's fixed set contains no 1024x768 and no 768x1024 — the two sizes a comic panel most wants — so those snap to 1200x896 / 896x1200. 16:9 is 1376x768, not 1344x768. `dhero` publishes three sizes in total. `klein` and the GPT-Image-2.5 pair take a range instead and keep the aspect exactly, with a total-pixel budget applied after the side bounds.

You already have `width`/`height` as image fields, so this may be nothing new — but make sure what lands there is my **returned** value, never the request's. The asked-for size is not recoverable from the pixels, and the actual size is not recoverable from the request, so if the two are conflated the record is simply wrong about the file with nothing able to correct it. It is also the same drift argument you accept for models: a provider can revise its published set, and a dated run of records is the only evidence it moved.

**`bytes`** — a fact about the file, cheap to keep.

**`usd` with `usd_estimated`.** Cost is already on your per-asset list; the flag is the part to keep beside it. Runware reports what it actually billed; the others are computed by me. A cost stored without the flag cannot be audited later. This matters more as of today: arcana-ai 0.5.2 prices OpenAI images and gpt-4o-mini-tts exactly, so the flag's value for those cameras is about to change from true to false. That is precisely why it has to be stored per asset and not inferred from the camera afterwards.

**`seed`, with a caveat you already know.** Only `klein` honours one; I return a seed only where it did something, so a stored seed means an attempt at reproducibility for `klein` and nothing for the rest.

For completeness, one thing that is NOT an asset: a `refused` status. It is unbilled, it is probabilistic — the same prompt may pass on a retry — and there is no picture, so there is no record to keep. I mention it only so a refusal is not mistaken for a failed write.

## 4. Styles: one real gap, the pixel tier

First, a correction to the question's framing: my cameras are not styles. A camera is a model. Style comes from the prompt, so the mapping you want is from my recipes, not from my cameras.

The gap: your vocabulary has `pixel` as a single value, and Silicon Circus keeps **three tiers as distinct, simultaneous deliverables** — `pixel-32` (detailed late-16-bit, the current standard), `pixel-16` (chunky early-16-bit), and `pixel-8` (reserved for the coarsest stage). They ship to separate directories and all are kept at once, because coarseness here is a **narrative degradation stage** rather than a style preference: the world pixelates as it comes apart. One `pixel` tag cannot tell `pixel-32` from `pixel-8`, which is the difference between the normal daytime look and the world falling apart. Either three values, or `pixel` plus a coarseness tag.

`3d-cartoon` does cover the mid-period CGI look I use for icon sets. Day and night map onto your separate `lighting` tag, which is the right place for them — with one warning: night in this world means the projectors are ON, so the pictures are radiant and floodlit, not dark. If `lighting` ever takes values, "night" must not be allowed to imply darkness.

## 5. Types: the missing property is whether it tiles

The seven types fit what I make — venues are `prop` or `drop`, diorama layers `drop` and `scrim`, a depth map is a `map`. The one property with no home is whether a picture **repeats**. A boardwalk backdrop is built to tile horizontally, and whether it does is a hard fact about the pixels: the seam either matches or it does not. It is decided by projection — a flat tileable plank texture tiles and still reads as having depth, a horizontal vanishing point never will, however the picture is tagged. A scrolling strip is also simply much wider than any frame that will show it.

That is not a type and it is not a claim about what the picture shows, so neither list holds it. I'd suggest a field, as `view` is one: a program choosing a background needs to know before it draws, and it cannot find out by looking.
